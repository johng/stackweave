# ThreadSanitizer suppressions for the stackweave ext TSan runs (run_sanitizers_ext.sh).
#
# We instrument ONLY stackweave's extension (-fsanitize=thread) and run it under a
# stock free-threaded CPython.  TSan therefore sees every access in stackweave's C
# but NOT the interpreter's internal synchronization, so a handful of races
# *inside CPython itself* are reported that are not stackweave bugs and that stackweave
# cannot fix.  Suppress those by the CPython function/file they occur in.
#
# Keep this list MINIMAL and CPython-only.  Never suppress a frame in
# src/runloom_c/* -- those are real and must be fixed, not hidden.

# --- CPython free-threaded biased reference counting (Python/brc.c) ---
# Cross-thread refcount merge frees and re-mallocs _PyObjectStackChunk; the
# allocator's reuse synchronization is invisible to a half-instrumented build.
race:_Py_brc_merge_refcounts
race:merge_queued_objects
race:_PyObjectStack_Pop
race:_PyObjectStackChunk_New

# --- CPython interpreter/GC internals that touch shared objects ---
# (Add specific CPython functions here as broader suite runs surface them;
#  prefer the narrowest function name over a whole-file match.  Do NOT use a
#  blanket called_from_lib:libpython... rule -- every stackweave race is "called
#  from" libpython via cfunction_call, so that would hide real bugs.)

# --- CPython stop-the-world GC mark phase (Python/gc_free_threading.c) ---
# THE IMPORTANT ONE, and the reason to read the note below before adding to
# this file.  Ext-only reported three races in module_gcframes.c.inc
# (runloom_gcframes_visit_g / visit_snap) against a hub thread's
# runloom_pystate_load.  They are NOT real: the GC walk runs under
# stop-the-world, which is exactly the synchronisation a half-instrumented
# build cannot see, so TSan misses the happens-before edge and reports the
# pair as unordered.  Verified 2026-08-21 -- a gold run on a
# --with-thread-sanitizer CPython 3.14.4t reports NONE of the three.
#
# Suppressed on the CPYTHON frame (the GC entry points), never on stackweave's
# visit_g/visit_snap, per the rule at the top of this file: a genuine race
# between two stackweave threads inside those functions still reports, because
# neither of these frames would be on its stack.
race:gc_propagate_alive
race:gc_mark_alive_from_roots

# --- CPython I/O internals reached from fibers (fileutils.c, posixmodule.c) ---
# Uninstrumented CPython syscall wrappers racing on interpreter-owned state.
# Also absent from the gold run.
race:_Py_write_impl
race:os_fstat_impl
race:os_readv_impl

# --- CPython non-atomic eval-frame hook setter (Python/pystate.c) ---
# _PyInterpreterState_SetEvalFrameFunc stores interp->eval_frame with a plain
# (non-atomic) write, and _PyEval_EvalFrame reads it with a plain load + indirect
# call.  stackweave installs the seeded controller's frame-count eval-frame wrapper
# (STACKWEAVE_MN_PREEMPT_FRAMES; compiled only with RUNLOOM_MN_CTRL) EXACTLY ONCE for
# the process lifetime (runloom_preempt_install; it used to toggle per
# mn_init/mn_fini, which raced a foreign thread's frame dispatch into a NULL
# call -> SIGSEGV; that toggle is gone).  The lone remaining NULL->hook publish
# still trips TSan against a foreign thread already dispatching frames, but it
# cannot crash (monotonic store to a non-NULL aligned pointer; the reader sees
# the old default or the new hook, both valid).  This is an upstream FT gap (the
# setter/reader would need to be atomic); an extension cannot close it
# (_PyEval_StopTheWorld is not exported, and an atomic store on our side does not
# make CPython's load atomic).  Suppressed on the CPython frame, not stackweave's.
race:_PyInterpreterState_SetEvalFrameFunc

# ---------------------------------------------------------------------------
# KNOWN-NOISE THAT IS DELIBERATELY *NOT* SUPPRESSED
# ---------------------------------------------------------------------------
# Ext-only reports races whose SUMMARY frame is `memcpy`, with the two sides
# in CPython string/bytes code -- e.g. unicode_decode_utf8 (write, under
# runloom_fcontext_entry) vs PyBytes_FromStringAndSize (read, another thread).
#
# These are CPYTHON-INTERNAL, not stackweave's, and the ext-only harness already
# says so in its summary line. Gold (a --with-thread-sanitizer interpreter)
# reports NONE of them: with CPython instrumented, TSan sees the interpreter's
# own synchronisation and they resolve -- the same mechanism as the
# gc_propagate_alive artifacts suppressed above.
#
# CORRECTION, worth reading before "fixing" this. An earlier version of this
# note diagnosed them as coro STACK-POOL REUSE being invisible to TSan, and
# recommended adding __tsan_acquire/__tsan_release annotations in coro.c. Both
# halves were wrong:
#
#   * The stack depot hands stacks between hubs under runloom_global_stack_lock,
#     which on POSIX is a plain pthread_mutex_t -- TSan understands it natively,
#     so that handoff already has a visible happens-before edge.
#   * stackweave ALREADY implements TSan's fiber API in full. See
#     runloom_fiber_san.h / runloom_fiber_san_impl.h: __tsan_create_fiber,
#     __tsan_destroy_fiber and __tsan_switch_to_fiber are called from
#     runloom_coro_resume and runloom_coro_yield (fibersan_enter / left /
#     suspend / resumed) under __SANITIZE_THREAD__, so TSan tracks each
#     goroutine's stack history properly across context switches.
#
# So there is nothing to annotate. Anyone acting on the old advice would have
# reimplemented working infrastructure. NOT suppressed, because the only frames
# available to key on (memcpy, unicode_decode_utf8, PyBytes_FromStringAndSize)
# run constantly all over the interpreter, and suppressing them would blind
# this lane to a large class of real races to tidy eight lines of output.
#
# ---------------------------------------------------------------------------
# WHICH LANE IS AUTHORITATIVE
# ---------------------------------------------------------------------------
# Ext-only is a fast smoke test and is STRUCTURALLY unable to attribute any
# race that crosses the ext <-> CPython boundary: it cannot see CPython's
# internal synchronisation (stop-the-world, biased refcounting, the allocator).
# Every entry above exists because of that blindness, not because of a bug.
#
# GOLD is the verdict: STACKWEAVE_TSAN_PYTHON=<--with-thread-sanitizer CPython>,
# which instruments both sides.  Treat an ext-only report crossing that
# boundary as a SUSPECT, and confirm it under gold before acting -- doing the
# reverse cost a chunk of a session chasing an invariant that was never broken.
# tools/verify/tsan_gold_drift.py warns when gold has gone stale.
